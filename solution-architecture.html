DMU Workflow Platform

Solution architecture for a config-driven, multi-team maker–checker operations platform. This document maps stakeholder requirements to the delivered design, high-level components, and low-level design (LLD) per component.

Deliverable: React + TypeScript UI · FastAPI backend · SQLite (swappable persistence) · Provider-based integrations
Summary Requirements High-level architecture Components LLD by component Data model Key flows Extensibility

1. Executive summary

The platform is a metadata-driven workflow engine, not a single-purpose case app. Each business team owns its own fields, dropdowns, workflow states, and optional bulk-update behavior. Admin configures and bulk-manages data; Maker and Checker operate records through role- and state-aware screens with dual control where configured.

Architecture follows a modular monolith: clear domain boundaries inside one deployable backend, a separate SPA frontend, and a repository abstraction so the database layer can be replaced (e.g. PostgreSQL) without rewriting business logic. Cross-cutting concerns (identity, notifications, file storage, time) use provider interfaces with stub/local implementations suitable for enterprise integration later.

Design principles

  • Configuration-first — behavior from published team config, not hardcoded screens
  • Server-side authority — permissions and workflow rules enforced in services
  • CQRS-lite — writes through rich domain services; grid reads use index projection
  • Swappable persistence — services depend only on repository interfaces

Repository layout

  • backend/ — FastAPI application
  • frontend/ — React TypeScript SPA

5. Low-level design (LLD) by component

5.1 Presentation tier (React SPA)

Modules

  • App shell — team switcher, acting-as user (SOEID), role chip, nav, platform admins panel
  • WorkItemsPage — server query (search/filters/sort/pagination), bulk select, export, reminders, admin create/delete
  • WorkItemDetailPage — dynamic form from field schema + capabilities; tabs for comments, attachments, per-item audit; workflow action modal
  • AdminConfigPage — field designer, workflow designer, team settings, versions, create team
  • UploadCenterPage — template download, upload preview, commit, job history
  • TeamAuditPage — team-wide audit log with filters
  • FieldInput — renders control by field type (text, numeric, date, selects, boolean, calculated read-only)

Data flow

All API calls go through api.ts with header X-User-Id. Active team config is loaded in AppContext for grid columns and forms. No permission logic is duplicated in UI beyond enabling/disabling from server descriptors.

5.2 API tier (FastAPI)

Routers

RouterEndpoints (representative)

Composition root

deps.py wires SqliteUnitOfWork, providers, and per-request NotificationProvider. One UoW per HTTP request; commit() on success.

5.3 Configuration service

Entities

ConfigVersion contains FieldDefinition[], WorkflowState[], WorkflowTransition[], TeamSettings (bulk update flag, unique identifier key).

Lifecycle

  1. Admin edits draft (or clones from active when opening draft)
  2. validate() — unique keys, workflow graph, calculated expressions, bulk-update settings
  3. publish_draft() — status published; audit event config_published

Field access model

Per field, per role: visible, editable, optional editable_states[]. Drives both API validation and UI capabilities.

5.4 Workflow & work item service

Work item system columns

id, team_id, status, assignee_id, config_version_no, version (optimistic lock), last_transition_by, data (JSON map of dynamic fields).

apply_action (atomic unit)

  • Validate version, role, transition from-state, dual control, required comment/attachment
  • Validate field updates via ValidationService + role/state rules (admin bypass optional)
  • Recompute calculated fields via safe AST expression evaluator
  • Persist item, refresh index projection, write audit, optional notification

Capabilities descriptor

Returned with every detail response: visibleFields, editableFields, allowedActions (with blocked_reason for dual control), canReassign, canDelete.

5.5 Bulk ingestion service

Pipeline stages

  1. Store raw file (FileStorageProvider)
  2. Parse CSV/XLSX; match columns to field definitions + assignee_soeid (+ status on update)
  3. Normalize & validate each row; resolve identity via team unique identifier
  4. Classify: create | update | duplicate | rejected | unchanged
  5. Persist UploadJob + UploadRowResult[] in previewed state
  6. On commit: apply creates/updates in transaction; per-row audit; assignment notifications

Rules

Bulk update only if TeamSettings.bulk_update_enabled. Rows not in file are never modified. Duplicate detection: DB + within-file.

5.6 Grid query & export

QueryDescriptor

search string, filters (eq/contains on system or indexed fields), sort, pagination, optional id list for selection export.

Index projection

Table work_item_index: one row per (work_item, field_key) for searchable/sortable/filterable/unique-id fields. Updated on every work item save.

Export

ExportService uses same query semantics; columns = role-visible + exportable fields; Excel via openpyxl.

5.7 Audit & notifications

AuditService

Central writer for action types: create, field_update, workflow_transition, assignment_change, comment_add, attachment_add, bulk_update, delete, upload_*, config_published, team_created. Stores UTC; UI renders local time.

NotificationProvider

Interface send(team, type, recipient, subject, body, work_item_ids). Implementation appends to notification_outbox for demo; replace with enterprise mailer without changing callers.

5.8 Persistence layer (swappable)

Pattern

UnitOfWork exposes repository interfaces: teams, configs, work_items, comments, attachments, audit, uploads, notifications. Only repositories/sqlite/ references SQLAlchemy.

Migration path

Implement repositories/postgres/ with same interfaces; change factory in deps.py. Dynamic values map naturally to JSONB in PostgreSQL.

5.9 Identity provider

HardcodedUserProvider supplies SOEID, name, email, and global role per user. Header X-User-Id selects acting user for maker–checker demos. Replace with SSO/entitlements adapter implementing CurrentUserProvider.
